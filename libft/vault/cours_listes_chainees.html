CHAPITRE 1

Une struct, c'est un paquet de variables

Une struct regroupe plusieurs variables (des champs) sous un seul nom. En mémoire, les champs sont collés les uns après les autres, dans l'ordre où tu les déclares.

struct s_point
{
    int x;
    int y;
};

struct s_point p;       // une variable de type "struct s_point"
p.x = 3;
p.y = 4;
p.x0x7ffc00
3 (4 octets)
p.y0x7ffc04
4 (4 octets)
sizeof(p)
8 octets au total

typedef : un raccourci de nom

Écrire struct s_point partout, c'est lourd. typedef crée un alias. La norme 42 veut s_ pour la struct et t_ pour le typedef.

typedef struct s_point
{
    int x;
    int y;
}   t_point;            // maintenant "t_point" == "struct s_point"

t_point p;

Le point . ou la flèche -> ?

Tu as…Tu écrisÇa veut dire
une struct t_point pp.xle champ x de p
un pointeur t_point *ptrptr->xexactement (*ptr).x : va à l'adresse, prends le champ x
Règle simple : à gauche du . il faut une struct, à gauche de -> il faut un pointeur vers une struct. Avec les listes, tu manipules quasiment toujours des pointeurs, donc -> partout.
Piège de priorité : *ptr.x se lit *(ptr.x), ce qui ne compile pas. C'est justement pour ça que -> existe.

Q1. t_point *a = &p; : comment mettre y à 10 via a ?

a est un pointeur, donc ->. L'autre forme valide serait (*a).y = 10;.

Q2. struct { char c; int n; } : quel est son sizeof sur ta machine 64 bits ?

Padding : un int doit commencer à une adresse multiple de 4, donc le compilateur insère 3 octets vides après c. Moralité : utilise toujours sizeof, ne calcule jamais une taille à la main.
CHAPITRE 2

La struct qui pointe vers elle-même

Voici ta struct du sujet :

typedef struct s_list
{
    void            *content;   // la donnée (n'importe quoi)
    struct s_list   *next;      // l'adresse du maillon suivant
}   t_list;

Deux détails sont essentiels :

  • next est un pointeur. Une struct ne peut pas contenir une struct du même type, sinon sa taille serait infinie (elle contiendrait une struct qui en contient une, qui en contient une…). Un pointeur, en revanche, fait toujours 8 octets.
  • On écrit struct s_list *next et pas t_list *next, parce qu'à l'intérieur des accolades, le typedef t_list n'existe pas encore : il n'est créé qu'à la ligne } t_list;.
content+0void * : 8 octets
next+8struct s_list * : 8 octets
sizeof(t_list)
16 octets

Q3. Ce header compile-t-il ?

t_list  *ft_lstnew(void *content);

typedef struct s_list
{
    void            *content;
    struct s_list   *next;
}   t_list;
Le C se lit de haut en bas. Au moment du prototype, t_list est un nom inconnu, donc erreur. Le typedef doit venir avant les prototypes qui l'utilisent. (👀 Va jeter un œil à ton libft.h…)

Q4. Pourquoi struct s_list next; (sans étoile) ne compile pas ?

Le compilateur doit connaître la taille de la struct. Avec un pointeur, c'est 8 octets, point.
CHAPITRE 3

void *content : la boîte qui accepte tout

void * = « une adresse, sans savoir ce qu'il y a derrière ». C'est ce qui rend ta liste générique : le même t_list peut stocker des int *, des char *, des structs…

int     n = 42;
char    *s = "salut";

void    *a = &n;     // OK : n'importe quel pointeur se convertit en void *
void    *b = s;      // OK

*a;                  // ❌ interdit : on ne sait pas QUOI lire (1 octet ? 4 ? 8 ?)
*(int *)a;           // ✅ 42 : on dit au compilateur "c'est un int *"
((char *)b)[0];      // ✅ 's'
Conséquence clé : tes fonctions ft_lst* ne savent jamais ce qu'il y a dans content. Elles ne peuvent ni l'afficher, ni le libérer correctement, ni le transformer toutes seules. C'est pour ça que l'utilisateur leur passe des fonctions (del, f) : lui sait ce que c'est. On y revient au chapitre 8.
Attention : ft_lstnew ne copie pas le contenu. Elle stocke l'adresse telle quelle. Si tu lui passes l'adresse d'une variable locale qui disparaît ensuite, ton maillon pointe dans le vide.

Q5. node->content contient l'adresse d'un int. Comment lire la valeur ?

On caste d'abord le void * en int *, puis on déréférence. (int)node->content transformerait l'adresse elle-même en nombre (et tronquerait 8 octets en 4).
CHAPITRE 4

La liste chaînée : un jeu de piste

Un tableau, c'est des cases collées en mémoire. Une liste chaînée, c'est des maillons éparpillés n'importe où (chacun vient de son propre malloc), où chacun connaît l'adresse du suivant. Le dernier pointe vers NULL, c'est le panneau « fin ».

TableauListe chaînée
Accès au n-ièmedirect : tab[n]il faut suivre n flèches
Ajouter au débutdécaler tout le monde2 flèches à modifier
Taillefixée au mallocgrandit/rétrécit à volonté
Connaître la tailletu la stockesil faut compter en parcourant

Le vocabulaire

  • Maillon / nœud : un t_list alloué.
  • Tête (head) : le pointeur vers le premier maillon. C'est la seule chose que tu gardes : perdre la tête, c'est perdre toute la liste.
  • Liste vide : la tête vaut NULL. C'est une liste parfaitement valide, et tes fonctions doivent la gérer.

Fabriquer une liste à la main (sans malloc, pour comprendre)

typedef struct s_node
{
    int             value;
    struct s_node   *next;
}   t_node;

t_node  c = {2, NULL};
t_node  b = {7, &c};
t_node  a = {3, &b};
t_node  *head = &a;      // head -> a -> b -> c -> NULL

head->value;              // 3
head->next->value;        // 7
head->next->next->next;   // NULL

Dans la vraie vie (et dans ft_lstnew), chaque maillon vient d'un malloc pour survivre à la fin de la fonction qui l'a créé.

Q6. Pour allouer UN maillon, lequel est correct ?

sizeof(t_node *) = taille d'un pointeur (8 octets), alors qu'il faut la taille de la struct. C'est un bug classique, invisible sans valgrind/fsanitize : tu écris hors de ta zone.

Q7. Avec la liste ci-dessus, que vaut head->next->next->value ?

head → a(3), ->next → b(7), ->next → c(2). Chaque ->next = « avance d'un maillon ».

  CHAPITRE 6 · JEU
  
Chirurgie de pointeurs 🔪

  
Tout le métier des listes tient en ça : modifier des flèches dans le bon ordre sans perdre de maillon. Clique les instructions dans l'ordre que tu veux : elles s'exécutent en direct. Tu peux réutiliser une carte, et les cartes pièges existent.

  
Légende : bordure rouge = maillon perdu (fuite mémoire), pointillés = maillon libéré.

  

  

  

  

  

  

  

  

  

  

  
La leçon : avant d'écraser une flèche, demande-toi « est-ce que quelqu'un d'autre pointe encore vers ce qu'elle désignait ? ». Si non, sauvegarde d'abord l'adresse dans une variable temporaire.







  CHAPITRE 7
  
Pourquoi t_list **lst ? (le double pointeur)

  
En C, tout est passé par copie. Si tu passes un pointeur à une fonction, elle reçoit une copie de l'adresse. Elle peut modifier ce qui est pointé, mais pas le pointeur de l'appelant.

  


// Version 1
void reset(t_node *h)
{
    h = NULL;
}
// dans main :
reset(head);


// Version 2
void reset(t_node **h)
{
    *h = NULL;
}
// dans main :
reset(&head);

  

  

  

    
main : head@ 0x7ff00x1000 (→ maillon A)

    
reset : h@ 0x7fd0—

  

  
Lance une version.

  
Règle à retenir : si une fonction doit pouvoir changer QUEL maillon est la tête (ajouter devant, ajouter dans une liste vide, tout vider et remettre à NULL…), elle a besoin de l'adresse de la tête, donc t_list **. Si elle ne fait que lire ou modifier les contenus, t_list * suffit.

  
Avec t_list **lst :

  

    
ExpressionTypeC'est quoi

    
lstt_list **l'adresse de la variable tête de l'appelant

    
*lstt_list *la tête elle-même (le 1er maillon, ou NULL)

    
(*lst)->nextt_list *le 2e maillon. Parenthèses obligatoires : *lst->next = *(lst->next) ❌

  

  
Q8. Dans une fonction avec t_list **lst, la liste est vide. Que vaut quoi ?

    

    
Liste vide = la tête vaut NULL, donc *lst == NULL. lst lui-même, c'est &head : une adresse valide. (lst == NULL serait un appel bizarre, mais rien ne t'empêche de t'en protéger.)

  
Q9. *lst->next, le compilateur le lit comme…

    

    
-> est plus prioritaire que *. Et lst->next n'a pas de sens sur un t_list **, donc erreur de compilation. Mets des parenthèses.







  CHAPITRE 8
  
Les fonctions passées aux listes

  
Tu connais déjà les pointeurs de fonction (ft_strmapi). Ici, il y en a trois formes, et elles ont toutes void *, parce que la liste ne sait pas ce qu'il y a dedans :

  

    
ParamètreReçoitRenvoieRôle

    
void (*del)(void *)un contentrienlibérer un contenu (l'utilisateur sait comment)

    
void (*f)(void *)un contentrienagir sur un contenu « sur place »

    
void *(*f)(void *)un contentun nouveau contentproduire une version transformée

  

  
Erreur n°1 : ces fonctions reçoivent le content, pas le maillon. On passe node->content, jamais node.

  
Exemples de fonctions qu'un utilisateur de ta lib pourrait passer


// pour del : libérer un content qui est un simple malloc
free                                  // void free(void *) : même signature !

// pour del : content = struct qui contient elle-même un malloc
void    del_user(void *p)
{
    free(((t_user *)p)->name);
    free(p);
}

// pour f (iter) : modifier sur place
void    add_one(void *p)
{
    *(int *)p += 1;
}

// pour f (map) : fabriquer un NOUVEAU contenu, sans toucher l'ancien
void    *square(void *p)
{
    int *res = malloc(sizeof(int));
    if (res)
        *res = *(int *)p * *(int *)p;
    return (res);
}

  
Q10. Laquelle peut être passée directement comme del ?

    

    
La signature doit être exactement void (void *). int * au lieu de void *, ou un type de retour différent, c'est un type de fonction différent (warning, et comportement indéfini).

  
Q11. Pourquoi ft_lstmap a-t-elle besoin de del alors qu'elle sert à créer une liste ?

    

    
Si le 5e malloc échoue, les 4 premiers maillons (et leurs contenus) doivent être libérés avant de renvoyer NULL, sinon fuite. L'ancienne liste, elle, n'appartient pas à lstmap : on n'y touche pas. Et pense à tous les malloc d'un tour : qui a alloué quoi, qui le libère si l'étape suivante rate ?







  CHAPITRE 9
  
Libérer sans exploser 💥

  
Un maillon possède deux zones mémoire distinctes :

  

    
le maillonalloué par ft_lstnew
→ libéré par free

    
le contentalloué par l'utilisateur (ou pas !)
→ libéré par del

  

  
Les 3 règles d'or

  
    
    
  • Après free(x), tu ne touches plus à x->quoi_que_ce_soit. Même si « ça marche » chez toi, c'est un use-after-free.
    • 
    
  • Ce dont tu as besoin plus tard, sauvegarde-le AVANT de libérer.
    • 
    
  • Un pointeur libéré qui reste accessible = un piège. Si l'appelant peut encore s'en servir, mets-le à NULL (et pour modifier le pointeur de l'appelant… chapitre 7).
    • 
  

  
Q12. Ce code libère un tableau de 3 chaînes stocké dans une struct. Où est le bug ?


free(box);
free(box->strs[0]);
free(box->strs[1]);
free(box->strs[2]);
free(box->strs);

    

    
Il faut libérer de l'intérieur vers l'extérieur : d'abord ce qui est pointé par box, puis box. Même logique pour un maillon et son content… et pour un maillon et son next.

  
Q13. On veut libérer t_node *n puis continuer avec le suivant. Lequel est correct ?

    

    
Option 1 : use-after-free. Option 3 : on libère le suivant, et l'ancien est perdu (fuite). Option 2 : sauvegarde, libère, avance.

  
Outils pour vérifier : cc -Wall -Wextra -Werror -g -fsanitize=address détecte les use-after-free et les débordements. valgrind --leak-check=full ./a.out détecte les fuites (à ne pas combiner avec fsanitize).

  BOSS FINAL 👹
  
Prouve que t'es prêt

  
B1. ft_lstdelone(node, free); Juste après, peut-on lire node->next ?

    

    
« Ne libère pas next » veut dire que le maillon suivant survit, mais node lui-même est libéré, donc lire son champ next est interdit. Si tu en as besoin : avant.

  
B2. Pourquoi ft_lstsize et ft_lstiter prennent-elles t_list * et pas t_list ** ?

    

    
Lire ou modifier des contenus ne change pas la tête. Une copie du pointeur suffit, et tu peux même l'avancer librement.

  
B3. ft_lstiter(lst, f) avec f = add_one sur une liste d'int. La liste après ?

    

    
iter applique f sur place. C'est map qui fabrique une nouvelle liste et laisse l'originale intacte.

  
B4. t_list *a = ft_lstnew("hello"); puis ft_lstclear(&a, free);. Que se passe-t-il ?

    

    
Le content n'a pas été alloué. del doit correspondre à la façon dont le content a été créé. C'est la responsabilité de l'appelant, pas de ta lib, mais il faut le comprendre.

  
B5. Tu ajoutes 10 000 éléments un par un avec ft_lstadd_back. Pourquoi c'est lent ?

    

    
Pas de pointeur vers la fin dans t_list, donc il faut la rechercher à chaque fois. Bon à savoir pour lstmap : en gardant toi-même un pointeur sur le dernier maillon construit, tu évites ce coût.

  
B6. void (*f)(void *) contre void *(*f)(void *) : la différence ?

    

    
L'étoile collée à void fait partie du type de retour. Le (*f) entre parenthèses, c'est ce qui fait de f un pointeur de fonction.

  🧪 KIT DE TEST
  
Un main pour vérifier tes fonctions

  
À lancer une fois que tu as tout codé. Compile avec cc -Wall -Wextra -Werror -g -fsanitize=address main.c libft.a, puis refais un test avec valgrind sans fsanitize.


#include "libft.h"
#include <stdio.h>

void    *new_int(int v)
{
    int *p = malloc(sizeof(int));
    if (p)
        *p = v;
    return (p);
}

void    print_int(void *c)      { printf("%d -> ", *(int *)c); }
void    add_ten(void *c)        { *(int *)c += 10; }
void    *times_two(void *c)     { return (new_int(*(int *)c * 2)); }

void    show(char *name, t_list *l)
{
    printf("%s: ", name);
    ft_lstiter(l, print_int);
    printf("NULL (size %u)\n", ft_lstsize(l));
}

int main(void)
{
    t_list  *l = NULL;
    t_list  *m;

    show("vide", l);                              // vide: NULL (size 0)
    printf("last(vide) = %p\n", (void *)ft_lstlast(l)); // (nil) ou 0x0
    ft_lstadd_back(&l, ft_lstnew(new_int(2)));     // add_back sur liste vide !
    ft_lstadd_front(&l, ft_lstnew(new_int(1)));
    ft_lstadd_back(&l, ft_lstnew(new_int(3)));
    show("l", l);                                 // l: 1 -> 2 -> 3 -> NULL (size 3)
    printf("last = %d\n", *(int *)ft_lstlast(l)->content);  // last = 3
    ft_lstiter(l, add_ten);
    show("l", l);                                 // l: 11 -> 12 -> 13 -> NULL (size 3)
    m = ft_lstmap(l, times_two, free);
    show("m", m);                                 // m: 22 -> 24 -> 26 -> NULL (size 3)
    show("l", l);                                 // l inchangée : 11 -> 12 -> 13
    ft_lstclear(&l, free);
    ft_lstclear(&m, free);
    printf("apres clear: %p %p\n", (void *)l, (void *)m);  // (nil) (nil)
    return (0);
}

  
Attendu : aucune erreur fsanitize, et « All heap blocks were freed » avec valgrind. Le kit ne teste pas les échecs de malloc : pour ça, demande-toi ce que fait ton code à chaque malloc qui renverrait NULL.
